# Jリーグ欠場・復帰情報台帳：収集調査と仕様たたき台

作成日：2026-10-24（日本時間）／段階：仕様検討。実装・自動収集は未開始。

## 1. 目的と合意済み事項

- 個人がブラウザで閲覧し、既存の戦力評価・予想システムへ渡す欠場情報を管理する。
- 対象はJリーグ公式とJ1・J2各クラブ公式のニュース。登録選手の後追い情報はネット検索も使う。
- 取得情報を蓄積し、離脱・練習合流・ベンチ入り・試合出場などを時系列で確認する。
- システムは復帰候補と根拠を提示し、利用者のチェックで復帰を確定する。引退等は復帰と区別する。
- 続報がなくても台帳から自動削除しない。
- 現状はExcelで管理し、CSVを既存システムに渡している。既存システムは復帰見込み日経過で戦力に戻す。
- 新システムでの復帰未確認と、既存システムの日付による戦力復帰は別の状態として扱う。
- この資料は実装指示の完成版ではない。下記「提案」「未決事項」を確定事項として実装しない。

## 2. 調査方法と限界

公開ページを検索・閲覧し、記事の構造と情報のばらつきを確認した。全クラブの網羅調査、プログラムによる連続取得、RSS/APIの有無、取得許可・robots.txt、ページ送りの完全性は未検証。閲覧できたことは定期収集の運用検証を意味しない。古い記事は抽出仕様の検証用で、現在の欠場情報ではない。記事時点の大会と現在の所属区分を混同しない。

## 4. データ設計案

### 選手・所属

内部選手ID、表示名、公式表記、CSV出力名、別名、所属クラブID、所属の有効期間、公式プロフィールURL。氏名の空白除去は検索用に行い、原表記を残す。同姓同名・外国籍選手の表記揺れは自動で断定しない。年度別のJ1・J2対象クラブ台帳を別に持つ。

### 記事と抽出結果

記事ID、元URL、正規化URL、発表元、タイトル、公開日時、取得日時、更新検知用ハッシュ、抽出に必要な根拠、抽出方法・版、取得結果。記事の本文領域だけを対象にし、最新ニュース欄・プロフィール・過去の負傷談を現在の負傷と混同しない。本文保存の範囲は各サイトの条件を確認して決め、全文転載を前提にしない。

URLが異なっても同一事象なら経過を統合する。記事自体は両方保持し、矛盾を上書きで消さない。同じURLの訂正は変更履歴を残す。

### 離脱案件

案件ID、選手ID、理由、負傷箇所・診断名、受傷日、手術日、離脱開始日、日付の根拠、全治原文、期間の単位・上下限、起算日とその根拠、復帰見込みの期間、CSV採用日、採用根拠（公式／既存の目安／手動）、確認状態、管理終了理由。

全治の状態は「記載あり／未定と明記／記載なし」を分離。暦月を一律4週に変換しない。1選手の再負傷は原則別案件とし、関連付ける。複数案件がある選手は1件の復帰だけで戦力復帰と断定しない。

### 経過と利用者の判断

イベント種別、発生日、記事公開日、根拠記事ID、該当箇所、抽出した事実、システムの提案、確認・却下・保留、確認日時、復帰の有効日、確認メモ。判断日と実際の復帰日を分ける。

### 連携履歴

出力日時、対象件数、出力ファイルの識別情報、各行の案件ID、採用値、前回からの追加・変更・終了。復帰を確認しても過去記録は削除しない。

## 5. 後追い処理案

1. 台帳の未終了選手を対象に、氏名・別名・クラブ名と「復帰／全体練習／合流／ベンチ／出場／再負傷／手術／引退／移籍」などを組み合わせて検索。
2. 公式を優先し、報道は別区分で保存。検索結果の要約だけでは確定しない。本文未取得なら未検証と表示。
3. 過去記事の再掲載、期限付き移籍からの「復帰」、チームのJ1復帰、別人の話を除外。
4. 登録中の離脱案件より前のイベントは、その案件の復帰根拠にしない。
5. 直近の再負傷と復帰の情報が競合したら、両方を見せて要確認にする。
6. 候補を利用者に提示する。全体練習合流・ベンチ入り・試合出場を別の根拠として表示し、利用者が復帰をチェックする。
7. 引退・退団・移籍は専用の確認へ回す。シーズン終了後の引退発表で即時終了しない。対象クラブ間の移籍では追跡を継続する。

検索ゼロ、取得失敗、続報なし、台帳上の離脱継続は別状態。未出場だけで負傷継続を断定しない。公式試合記録から出場を確認する機能は有用だが、利用するデータ経路は未検証。ニュース検索のみで全選手の復帰を把握できる保証はない。

## 6. 画面案

- 主画面：クラブ別の未終了案件。選手、理由、開始日、採用見込み日、最新経過、記事の最終発表日、検索最終実施日を表示。
- 「見込み日経過・復帰未確認」を明示。予想側では日付により除外が終わる可能性があると表示し、実際の読み込みが未確認なら「反映済み」と断定しない。
- 確認待ち：新規離脱、復帰候補、期間修正候補、引退・移籍候補を根拠付きで確認。新規登録を毎回人が承認するかは未決。
- 選手詳細：案件別の経過、根拠記事、採用日付、手動変更履歴。
- CSV出力：前回との差分と未確定・不明値を確認してダウンロード。
- 収集状況：サイトごとの最終成功、失敗、次回予定。停止しても台帳を消さない。

## 11. 予想側コードの追加調査（2026-10-24）

利用者の許可を受け、予想プロジェクトを読み取り調査した。コード・元データは変更せず、予想全体も実行していない。上記の「予想側コード未参照」は本節追加前の状態。本節で確認できた内容を優先する。

### 確認した経路

scripts/run_batch_weekly.sh と run_batch_matchday.sh は、欠場管理リスト.csv と選手マスタを build_absence_impact.py に渡し、影響CSVと日付別スナップショットを生成後、11_prediction_01.py を呼ぶ。環境変数によるパス変更があるため、実際の利用者の実行設定は別途確認が必要。

11_prediction_01.py は、明示指定スナップショット、指定基準日以前のスナップショット（基準日指定がなければ最新）、通常の影響CSVの順で選択する。基準日以前のファイルがない場合は最新へフォールバックする。元CSVを出力しただけでは予想入力は更新されず、影響CSV・適切な日付のスナップショットの再生成まで必要。

### 既存認識の修正：復帰日は影響ゼロの日ではない

11_prediction_01.py の _absence_date_factor（11230行付近）は、復帰見込み日の前後で影響を線形に減衰する。

| 見込み期間 | 復帰見込み日の前後に設ける幅 |
|---|---|
| 4週以下 | 前後1週 |
| 4週超〜12週 | 前後2週 |
| 12週超〜24週 | 前後3週 |
| 24週超 | 前後4週 |

開始日より前は0。減衰開始日までは1、復帰見込み日は0.5、減衰終了日以降は0。expected_weeksが空欄・非正値なら開始日と復帰日から期間を求めて幅を選ぶ。

関数定義だけを分離して試算（予想処理全体やファイル出力は実行せず）：開始2026/10/17・6週・見込み日2026/11/28では、11/14=1、11/27=約0.536、11/28=0.5、11/29=約0.464、12/12=0。

### 列・欠損・重複の扱い

- origin_competition_key と applies_across_competitions は、build_absence_impact.pyでは出力に引き継ぐが、調査した11_prediction_01.pyの欠場判定では参照しない。この経路ではフラグを0にしても大会による選別は働かない。名前の意味と実装の実効性を区別する。
- absence_typeも日付係数の分岐に使われない。cardにも負傷と同じ減衰がかかる。例：開始10/23・見込み復帰10/30・1週のcardは、10/24の係数が約0.929になる。これは日付係数単体で、最終予想への補正率そのものではない。
- 復帰日が空欄なら開始日＋expected_weeks×7で補完。日付が揃わず旧形式のround_startもなければ、その行の係数は0。無期限の除外としては働かない。
- 同一選手の複数行を案件別に処理し、最終的にチーム×試合で合計している。選手単位の重複排除はなく、重なる離脱・cardをそのまま複数出力すると二重計上の可能性がある。
- availabilityは既存入力の任意列。未入力ならout、doubt等は影響0.5、returned等は影響0にする。ただしreturnedは行全体を0にするため、過去試合の再計算で元の離脱影響を失う可能性がある。復帰日の履歴管理の代わりに安易に使わない。
- noteに説明文が付いた現CSV見出しは、load_absencesの列対応表と一致しない。標準note列が空で補われるコードになっており、元のメモが影響CSVに引き継がれない構造。新出力は正規のnote列にする提案。ただし実ファイルを通した互換確認は未実施。
- 各実行はその時点の入力から影響CSVを全件再生成する。行削除が通常CSVへ反映されても、過去スナップショットは別ファイルとして残り、採用ファイルによって予想に使われる行が変わる。

### 新システムへの反映案（未承認）

1. 台帳の「復帰確認」と既存予想の「日付減衰」は別管理し、確認済みの復帰を正確に反映する方法を連携仕様として選ぶ。
2. 10列互換出力で収集・更新の価値を先に得ることは可能だが、見込み日に係数0にはならず、cardと負傷の違いも解決しない。その限界を明示する。
3. 正確な連携には、予想側に「確認済みの復帰有効日」「負傷の見込み減衰」「出場停止の対象試合」を区別する小さな受け口を追加する案がある。別システム全体を作り直す話ではない。現段階では変更しない。
4. 台帳では案件単位で履歴を保持し、予想用には選手×対象試合で重複しない出力方式を検討する。10列のみで全ケースを表現できるとは確定しない。
5. 出力プレビューと前回差分に加え、予想に採用されたスナップショットの日付・生成成功を確認する運用が必要。

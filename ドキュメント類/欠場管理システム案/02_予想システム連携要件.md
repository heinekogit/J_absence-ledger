## 2. 連携を2段階に分ける

### 段階A：現行互換

既存10列CSVを新台帳から出力する。公式・後追いの情報を利用者が採用し、復帰見込み日を更新できる。既存の減衰方法は維持する。この段階だけでは「復帰確認の有効日から必ず影響0」「cardの対象試合だけ除外」は実現しない。

日付を極端にずらして無期限離脱や即時復帰を表現しない。復帰済み行の削除は過去予想にも影響し得るため、履歴・スナップショットの運用を含めて決める。終了案件をどの範囲まで出力するかは実装時に検証する。重複案件の互換10列での表現が曖昧なら確認待ちにし、黙って合計しない。

### 段階B：確認済み情報を正確に渡す拡張（提案）

既存10列を維持しつつ別の版付き連携ファイル、または拡張列を追加する。形式は実装時の契約テストで選ぶ。収集側の内部データをこの10列に制限しない。

必要な意味：schema_version、export_id、case_id、player_id、club_id、absence_type、absence_start_date、expected_return_date、expected_return_basis、confirmed_return_date、closed_reason、closed_effective_date、competition_scope、suspended_fixture_ids、recorded_at、source_published_at、confirmed_at。既存の氏名・クラブ表記との対応表も提供する。

calendar上の発生日とシステムが知った日時を分離する。根拠や利用者確認が後日得られた場合、過去時点で既知だった情報と混同しない。

## 3. 拡張後に満たしたい振る舞い（採用前に確認）

- 負傷の復帰未確認時は、既存の見込み減衰を既定として維持する案。見込み日超過で自動延長しない。
- 復帰確認後は、確認済み有効日以降、その案件の欠場影響を0とする案。過去の離脱期間は残す。有効日当日の試合を対象にするかは利用者と確認する。
- 早期復帰も長期化も、有効日・根拠・採用履歴付きで反映する。
- 複数案件が重なる選手は、選手×クラブ×対象試合で一度だけ戦力除外する。係数の結合は最大値を初期案とし、加算しない。戦力の数値計算は既存側に置く。
- cardは確定した停止対象試合で係数1、その他は0とする案。大会・試合延期・複数試合停止・他大会処分を考慮し、発表日や7日単位で代用しない。不明は要確認にする。
- 引退や移籍による管理終了は負傷復帰とは区別。選手マスタの所属・在籍との責任分担を決め、欠場データだけで所属変更を推測しない。
- 全治不明の未終了案件の予想反映方針は未決。日付空欄で無期限除外になると誤認させない。

## 4. スナップショットと再現性

出力版と影響CSV・スナップショットの元export_idまたはハッシュを対応付ける。予想側は採用したファイルと基準日を記録し、台帳は受領確認がない限り「出力済み」とだけ表示する。

過去時点の再現では、その時点以降に得た復帰情報を使わない。基準日以前のスナップショットがない場合、現行の最新へのフォールバックをそのまま使ってよいか検討する。基準日を付けただけで当時既知の情報になるとは限らない。

## 5. 連携受入テスト

| ケース | 確認事項 |
|---|---|
| 従来10列入力 | 拡張情報なしでは既存結果を変えない |
| 復帰見込み日前後 | 現行減衰と新しい確認済み復帰の優先順が明確 |
| 早期復帰・延期 | 有効日の前日・当日・翌日を確認 |
| 過去時点再現 | 後日判明情報で過去スナップショットを上書きしない |
| 重複記事・再負傷・card重複 | 同一選手を二重計上しない |
| card | 対象試合のみ、複数試合・大会・延期に対応 |
| 空欄・全治不明・期間幅 | 暗黙の復帰や無期限離脱を作らない |
| CSV更新のみ・変換失敗・古いスナップショット | 未反映を検出し、成功表示しない |
| noteにカンマ・改行・日本語 | 元値が引き継がれる |
